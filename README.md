# Bank Bank
#### Video Demo:
#### Description:
Bank Bank is a banking simulator web application made with Django and JavaScript with some help from the Google Charts data visualization API.
Users can make an account with Bank Bank, send and receive funds to other user's accounts, move their own funds between their Checking and Savings accounts and see detailed transaction histories for both these accounts like any boiler plate banking website. To encourage and empower Bank Bank users to manage their money well and be financially healthy, Bank Bank allows users to create and save categories to their transactions. These categories then open up opportunities for using their own data to get Spending breakdowns to see where their money is going in the last week, month, year, etc. As well as general spending, users can also see their spending breakdown as a percentage of their paycheck. Users can also track their savings progress and perform searches to find specific past transactions that meet their criteria.




### Distinctiveness and Complexity:
This project is distinct from the previous CS50 Web assignments mainly due to the fact that it generates significant numerical data and puts it to use with the help of Google Charts. The data generated by the usual behavior of a user sending and receiving money opens up interesting possibilities where that data can be accessed by the user themselves in useful ways. To do that this project involves more specific filtering and aggregating of its data than the previous projects. For example for the Search element of the project, Transaction objects need to be filtered by date, by an iexact lookup for the username of the other sender/receiver or even by category, where a user's Category objects need to be filtered and then matched to Transaction objects to perform a successful search query.
This functionality is extended when using the various budgeting/data visualization aspects of the site where transaction and category objects must be filtered and then processed by the projects API views in order to return properly formatted data to input into the Google Charts API.
Finally this project also goes deeper with improving upon the look of the site using CSS and Bootstrap to get closer to the appearance of a real banking website.



### Project Structure:
This project comprises the usual Django structure of the app files in the 'bank' folder, other more under-the-hood files in the 'capstone' folder, the SQLite3 database file, the manage.py file and this README file. In the 'bank' file we have the Migrations, the Static files where the CSS and Javascript files are found as well as the HTML templates.
These include the Layout file which sets out the background structure for all the other files to extend on top of. We have our usual Register, Login, Index, Account, Error, Transfer and Search files which simply render the data passed to them by the Views file. We also have the more complex Paycheck, Savings and Spending files which also contain their respective JavaScript code from the Google Charts API.




#### Views.py
The views file imports all of the necessary Django modules for the app, the Forms and Models as well as Json, Datetime and Random Python external libraries.


Index --  this function initializes the user and their two accounts, then passes these to the Get_transactions function to get all the relevant transaction history data and any Category object data attached to these. For the index page the transaction history is limited to the latest 5. The transactions and their amounts are passed to an inner function(get_balances) to generate a balance history to display alongside these transactions, so the user can see how their account balance got to the number it currently displays. Finally it initializes the Transfer form to allow the user to move funds between their Checking and Savings accounts. We then render with the index.html file.


Account -- this allows the user to see a complete history of their transactions, balances and categories for a single account. The same details are then rendered with the account.html file.


Get_Transactions -- this function is key to the two previous functions. It takes two parameters, an account and the number of transactions to limit to. A filter query is then performed using the Q module (effectively an 'either/or') which returns all transactions where the account in question sent or received funds. We then get a list of these transaction ids and query our Category objects to find any that match these transactions and our user. We then return these as a dictionary to plug them into our templates next to the corresponding transaction.


Chart_data -- this is the API which returns a JSON-style array of data to the Google Charts API to display our Spending breakdown. It takes a time period as a parameter then filters all our outgoing Checking transactions for the current week, month, quarter or year. We then loop through our transactions, matching them to any Category objects the user might have created for them. We then create a dictionary of totals for any Categories while adding uncategorized transactions to an Unclassified total, this dictionary is then passed to the JS fetch call to use with Google Charts.


Spending -- a simple view to initialize the Spending breakdown page with its select bar(Period_form) to allow the user to toggle between periods when viewing their Spending data which will display as a donut chart, renders to the Spending.html template.


Paycheck_data -- another API similar to the chart_data API. This API also gets a user's relevant data determined by the time period parameter. It filters for outgoing checking transactions and any matching Category objects made by the user. It also searches for an incoming transaction in the respective time period which has been categorized as 'Income', if none is found the user will see a message to first categorize their monthly paycheck. The transactions and categories are then looped through and aggregated as a percentage of the paycheck and any left-over balance is added to the data as 'Remaining Balance'. The data is then formed into a list of lists to meet the requirements to work with the Google Charts stacked bar chart.


Paycheck -- initializes the form to allow the user to toggle time periods and renders the paycheck.html template.




Filter -- this function takes a list of transactions, an account(eg. Checking or Savings) and a user along with some search parameters to systematically filter those transactions to meet specific criteria such as a time period, another user's username and/or a Category made by that user. If any transactions meet all the criteria they are returned as a list otherwise an empty list is returned


Search -- this view handles Get and Post requests where a user can see a form to search their own transactions and upon submitting the form via Post, have their transaction history filtered (with the above Filter function) by their desired metrics. Results are then returned and displayed, rendering back to the search.html template.


Ex-transfer -- this view handles Get and Post requests when a user wishes to transfer funds to another user's account. With a Get request we render the form to specify the user's username and an amount. When submitted via Post the external user, their account is checked for and we check the current user/sender's balance is sufficient (if not, they are returned an error message on the Error template). If all is well, a new Transaction object is initialized, saved, the two user's account balances are updated and the current user is redirected to their index page where they will see it as their latest transaction.


Internal_transfer -- this function handles Post requests when a user submits the Transfer form from the Index page. We check the form is valid, the user is authenticated and that there are funds to make the transfer. A Transaction is then initialized, saved, the balances of the two accounts adjusted and the user is reversed back to the same index page if successful. If the amount is more than the balance or they are trying to send Savings to Savings, etc., they are shown an error.


Login_view --  a boiler-plate login function to check a user's credentials and log them into their account, then return them the index page if successful or ask them to try again with an error message otherwise.


Logout -- logs the user out.


Register -- if the request is Get, show the user a form to create an account with Bank Bank. If via Post, check if the two passwords match and the username is available and if so create the User object as well as two Account objects (Savings and Checking), then reverse them to the index page after login them in. Otherwise show an error message and prompt to try again.


Categorize -- the API which allows users to make a Put request where a user can create a Category for their Checking transactions. After getting the request data, we query for that transaction, check for an existing Category object created by the user. If none is found, create a new Category and save it. If a previous category exists, reclassify it with the data from the request (perhaps the user classified it wrongly in the past and is now correcting it.)


Savings -- this function initializes the form to allow the user to toggle between time periods and render the savings.html template.


Savings_data -- this API function initializes the user's savings account and its transaction history, filters it for the desired time period given in the parameters. It then loops through the transactions for additions and subtractions to the accounts balance and the dates of these changes are all added to a list which is returned as a Json array to be used by the Google Charts API and turned into a line chart. If multiple transactions are made on the same day these are combined to avoid awkward data being displayed on the chart.




#### Models & Forms


Models:


User -- inherits entirely from Django's AbstractUser


Account -- this model requires a User, a Type (Checking or Savings), a balance, 4 digits (to simulate the last 4 digits of a real bank account code) and a boolean overdrawn or not status. A str function and a serialize function are included.


Transaction -- takes the time at creation as a timestamp, the sending account as Sendaccount, the reciever as Receiveaccount, the amount and a boolean Selftransaction to signal if the user is sending between their own two accounts. Str and serialize functions are included in the class.


Category -- this model takes a user who created the classification, the transaction it matches to and the name of the category. It includes both str and serialize functions.


Forms:
Transactions form -- takes a Receiver (ie. username) as a string and an amount as a float.


Transfer form -- specifies two lists of account choices to select from ("", Savings, Checking), choice fields to send from A to B and an amount as a float field.


Period form -- includes a series of time periods (Week, Month, Year) to select from.


Month form -- includes a choice of This month or Last month




#### Bank.js
The main JavaScript code used by this project.
Once the document has loaded we listen for a series of events depending on what template we are currently rendering.
If we are on the Transfer template we listen for changes to the form inputs and once the user has finished inputting the transaction details, we display these below the form.


If the user is on a page displaying Checking transactions, they will see a button to Categorize or re-categorize their transactions. We listen for clicks on these buttons then replace them with a select form where they can choose a Category and save it. These changes are all performed client-side. The categorization is also sent to the database via a Put fetch call to the Categorize path so they will see the same Category when refreshing the page.


The user can also perform an internal transfer client-side, after completing the form on the index page, a Post request is made via fetch through the Inttransfer path.




#### Paycheck, Savings & Spending templates and the Google Charts API
These three html files include the Google Charts API packages which allow us to, after fetching the data from our own API functions, then initialize and draw a bar chart, line chart or donut chart visualizing our data. The pages also listen for changes to the time period toggle at the top of the page, allowing the user to see the differences in their spending/savings habits.
